# 2026-09-13 —— 集合通信 A/B、窗口对 KV 池的代价,以及一个负结果

两项改动在同一套四节点环网、同一权重、同一服务端构建、同一天,用受控协议做了对比:

1. **集合通信** —— 换成 **FujitsuPolycom/sparkring**(Apache-2.0)发布的 switchless-ring 版本
   NCCL 及其环境变量,同时启用双 HCA 并固定通道数;
2. **Engram 读路径** —— 他们的 `BALANCED`(hash 列跨 rank 交错)加打包单次读分片,对上一个
   **本来就把每 rank 的 Engram 行落在本地 NVMe** 的部署。

其余全部保持不变:`1M` 窗口、CUDA graphs(`FULL_AND_PIECEWISE`)、视觉 + 工具调用、
DSpark `k=5`、block 128、`gpu-memory-utilization 0.84`、每节点一个 rank、TP=4 走直连环网。

口径说明:下文每次对比的两侧跑的都是**同一份 checkpoint**;通信层与 Engram 的结论属于
通信与 I/O 路径的性质、与具体权重无关,但**绝对吞吐在不同 checkpoint 间会浮动几个百分点** ——
可以搬走的是**差值**。

本报告的规矩:**只有能重复出来的数字才会被写成结论。** 这台硬件上单次吞吐测试的
run-to-run 波动是 **每个并发档 ±5~9 %**,所以基线先跑 **两遍** 才允许下判断。

## 1. 通信层 A/B —— 改了什么、换来了什么

| 指标 | 基线(第 1 遍) | 基线(第 2 遍) | switchless 通信 | 判读 |
|---|---:|---:|---:|---|
| C1 聚合 / 单流 tok/s | 43.26 / 48.91 | 46.10 / 52.51 | 47.87 / 53.31 | 噪声内 |
| C2 聚合 / 单流 | 74.15 / 43.01 | 71.49 / 40.81 | 79.34 / 45.78 | +7~11 % |
| C3 聚合 / 单流 | 85.75 / 33.60 | 93.21 / 35.81 | 97.00 / 36.96 | 噪声内 |
| **C6 聚合 / 单流** | 136.76 / 26.17 | 134.31 / 26.01 | **153.33 / 29.30** | **+12~14 %** |
| 冷 prefill 2K / 8K / 32K tok/s | 1259 / 934 / 1309 | 1636 / 1450 / — | 1639 / 1821 / 1908 | 区间顶部 |
| 2 路并发聚合(冒烟) | 123.0 | — | **144.6** | **+17.6 %** |
| 1M 档 KV 池(tokens) | 1,700,113 | — | 1,742,812 | +2.5 % |

**我们主张的**:C6 的增益是**真的**(两次基线都低于它,而 C6 正是 TP=4 all-reduce 开销显形的地方),
2 路聚合跟着一起动。
**我们不主张的**:C1/C3 的改善,以及任何精确的 prefill 百分比 —— 基线自己的 prefill 就在
934~1636 tok/s 之间飘。

**没有变化的是**:单流延迟(C1)。单个请求几乎没有集合通信可优化 —— **如果你的负载是一问一答,
这项改动对你没有价值**;它只在并发下兑现。

### 产生这组数字的配置

```
# 通信选择(四台完全一致)
NCCL_ALGO=Ring
NCCL_NET=IB
NCCL_IB_HCA=<roce-netdev-a>,<roce-netdev-b>   # 两个 RoCE 设备,对应环的两个方向
NCCL_IB_GID_INDEX=<gid>                        # 必须非全零 GID;全零 = 没配成 RoCE
NCCL_IB_SUBNET_AWARE_ROUTING=1
NCCL_IB_SUBNET_PREFIX_LEN=24
NCCL_SKIP_TREE_CONNECT=1
NCCL_MIN_NCHANNELS=4
NCCL_MAX_NCHANNELS=4
NCCL_PROTO=LL,LL128,Simple
NCCL_P2P_LEVEL=SYS
NCCL_CROSS_NIC=1
NCCL_IB_MERGE_NICS=0
NCCL_CUMEM_ENABLE=0
NCCL_SWITCHLESS_RING_ONLY=1                    # 只在下面这个打过补丁的 NCCL 里存在
```

switchless 版本还需要在容器里用 `LD_PRELOAD` 预加载它自己的 `libnccl.so.2`(2.30.7),
而不是用 pip 轮子里带的 NCCL。

**库从哪来(不用拉他们那个好几 GB 的镜像)**:他们的 GitHub **release 资产**
`native-runtime-files-<date>.tar` 里就有 `native/libnccl.so.2.30.7` —— aarch64、
`NCCL version 2.30.7 compiled with CUDA 13.3`,并且带 `ncclParamSwitchlessRingOnly` 符号。
想自己编的话,源补丁在 `spark_transport/nccl/*.patch`,构建脚本在
`runtime/sparkring/jovian-r33/build_nccl.sh`。

⚠️ **通道数很关键。** 在这套环网上用别的通道设置,我们此前遇到过 NCCL 初始化阶段的
`ibv_modify_qp` 超时。这里验证过的是 **4**;其它值请当作需要在你自己环网上验证的实验。

## 2. 满 1M 窗口下,`--gpu-memory-utilization` 与 KV 池

同模型、同功能(graphs + 视觉 + 工具 + `k=5`)、同窗口(1,048,576),只有显存利用率不同。
池子 token 数与请求长度是 **1:1** —— 一个 1M 请求占 1M 个池 token,不是倍数关系。

| `--gpu-memory-utilization` | 实测 KV 池(tokens) | 可常驻的满 1M 请求 | 样本数 |
|---|---:|---:|---:|
| 0.83 | 1,484,371 – 1,597,326 | 1.42 – 1.52× | 4 |
| **0.84** | **1,700,113 – 1,870,320** | **1.62 – 1.78×** | 3 |

两条运维提醒:

* 同一份配置**换个启动批次落到的池子大小不同**(约 ±7 %),因为图/探测期的分配与碎片不一样 ——
  别把单次启动的读数当成"池子就是这个大小";
* 提高这个比例是**保住窗口**换并发的办法;为了池子去砍窗口是反方向的交易,代价是上下文。

## 3. 负结果:Engram 打包没能迁移过来

SparkRing 记录 `BALANCED`(hash 列交错)配合打包单次读分片可带来 **prefill +12~18 %**、
突发 TTFT −13 %。

我们这里实测:**没有增益**(各档都在噪声带内,两个方向都试过)。
原因在它对比的基线:他们的比较对象是 **打包分片(每行一次 pread) vs 原始 checkpoint 分片
(每行两次 pread,权值与 scale 相距约 24 GB)**;而我们的部署**本来就把每 rank 的 Engram 行
落在本地 NVMe**,早就在单次读路径上 —— 没有那第二次 pread 可以省。

**通用教训:** 采纳任何公开优化前,先看清它的基线。如果你的部署已经具备该优化所添加的性质,
那个数字对你不可用。把负结果写出来不花成本,却能替别人省掉一轮起服。

## 4. 这些数字是怎么量出来的

* **吞吐网格**:8 个提示类别 + 一个计数上限提示,各跑并发 1/2/3/6;token 数取服务端
  `usage.completion_tokens`;temperature 0、关思考;各次启动用同一套题(构造上就是冷前缀)。
* **冷 prefill**:每个目标长度用唯一填充前缀;TTFT 取首 token 时延,prefill 速率 = prompt tokens / TTFT。
* **KV 池**:直接读引擎启动时自报的那一行,不靠估算。
* **验收闸门**(配置要被留下来,必须全过):冒烟 + 用 `logprobs` 做 NaN 探针(NaN logits 会让 API
  直接拒绝序列化)、三种温度下的 30 次生成 garble 闸、30 题正确性、视觉 + 工具调用 7 项
  (图由进程内确定性生成)、拒绝率探针、12 题能力集。
* **重复**:任何改动配置的主张,基线都要**跑两遍**、候选跑一遍;**候选没有同时胜过两次基线,
  就按噪声上报**。这条纪律是这台硬件上"我们把 X 提升了 15 %"还能算诚实的唯一原因。

## 5. 公网路径上的服务遥测

与 6.7 节同一配置,但这次是**经过部署的公网网关**测量(TLS + 隧道 + 代理各一跳),因此是
客户端真实看到的数字,而不是引擎侧计数:

| 项目 | 数值 | 备注 |
|---|---:|---|
| 单流稳态 decode | **~50–53 tok/s** | 引擎侧 C1 单流,多次重复 |
| 单流上限(快速/计数类内容) | **~86 tok/s** | 最佳类别 |
| 端到端,生成 700 token | **~55 tok/s** | 走公网,含首字等待 |
| 端到端,生成 273 token | ~27 tok/s | 短输出被首字摊薄 —— 不是 decode 指标 |
| 2 路并发聚合 | **~132 tok/s** | 实时实测 |
| 6 路并发聚合 | **~153 tok/s** | 换通信层后观测到的最好值 |
| prefill,3.5K 提示 | **~1,960 tok/s** | 长上下文 prefill 落在 900–1,900 区间 |
| 首字延迟(短提示) | **~1.4 s** | 公网往返 |
| 1M 窗口的 KV 池 | **1,870,320 tokens** | 窗口的 1.78 倍 |

怎么读这组数:**单流 decode ≈50 tok/s,不随通信层改动变化**;通信层的收益体现在并发上
(2 路 ≈132,6 路 ≈153)。短输出走公网看起来更慢,是因为首字占了主导 —— 要测 decode 请用
≥500 生成 token,或者直接读引擎侧数字。
