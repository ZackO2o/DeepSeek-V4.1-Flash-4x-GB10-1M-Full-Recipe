# 一条两节点车道:EXL3 2.9 bpw、Engram 落盘,以及那个真正移动内存墙的旋钮(2026-09-17)

> 本文**不是**第二份四节点实测。它是**另一条车道** —— 之所以公开,是因为其中两条结论讲的是
> **1M 配置为什么装得下**,而不是它跑得多快。

## 车道

| | |
|---|---|
| 节点 | **2 × GB10**,每台 128 GB 统一内存(可见 121.69 GiB) |
| 并行度 | TP = 2(因此每 rank 约 98 GiB 权重) |
| 基座包 | **EXL3 2.9 bpw**,39 分片,`total_size` **210,713,013,432**(196.1 GiB)—— 量化包,不是原生 FP8 |
| 上下文 | **600,000**(`--max-model-len 600000`) |
| 能力 | 视觉 + 工具开,`cudagraph_mode FULL_AND_PIECEWISE`,DSpark k=3,关闭思考 |
| Engram | **打包到节点本地 NVMe**(`start.sh pack`,每 rank 每表 47.2 GiB ≈ 94 GiB/节点,456 MiB/s,约 8 分钟) |
| 附加 | cooperative MoE 内核(本地编译并过门,见下) |

以下全部在这条车道上实测。绝对 decode/prefill 数字**不可**与主 README 的四节点原生 FP8 表格相比 ——
有价值的是下面两个效应的**方向**。

## 发现 1 —— `--max-num-batched-tokens` 比 `--gpu-memory-utilization` 更能移动内存墙

我们撞上了主 README 记录过的同一堵墙("600K 在 0.80 起不来"):预检差约 **1 GiB**。
往下走 GMU **没有**修好它 —— 0.88 → 0.86 → 0.84 只是把墙挪了个位置,池子缩小让出的余量
又被别处吃掉。

真正把余量拿回来的是把批 token 预算从 **1024 提到 1536**:

| `MAX_NUM_BATCHED_TOKENS` | 起服时 head 的 `MemAvailable` |
|---|---|
| 1024 | **0.09 GiB** |
| **1536** | **3.50 GiB** |

**更大的 chunk 留下了更多余量。** 可能的机理是调度轮次:chunk 更大 → prefill 调度迭代更少 →
同一时刻存活的临时工作区更小。而 1536 恰好也是视觉塔需要的值(单个图像项在 chunk 里可能占
约 1025 token),所以在这个模型族上它**不是取舍**,而是本来就该用的值。

**必须说明的前提**:这是在**两节点 + 量化包**上量的。我**没有**在四节点 + 原生 FP8 上复现过,
所以才放在 issue/结果文档里,而不是直接改主调参表。

## 发现 2 —— GB10 上的 `MemAvailable` 是"地板",不是"仪表"

在这条车道上跑完一次长 prefill 后,head 报 **2.35 GiB**;服务期间它**经常读到 0.00 GiB**,
而服务照常应答,且**真实 OOM-kill 为 0 次**(`journalctl -k` 中没有 `oom-kill` /
`Out of memory: Killed`)。

原因正是主 README 解释池子行为时给出的那条:GB10 上约 98 GiB 的权重活在**不计入任何进程 RSS 的
驱动分配**里,于是内核的"可用"估计没什么可算的,长期贴在 0 附近。两个直接后果:

* **以 `MemAvailable` 为判据的看门狗,阈值必须按车队分别设定。** 同一个量在四节点车队
  (issue #1)读 **10.3 GiB**,在这里读 **~0**。阈值跨车队搬运的结果只有两种:永不触发,或一直误报。
* **能跨车队活下来的信号是**:内核真的打出 `oom-kill` 那一行、容器健康/重启状态变化,
  以及**长 prefill 之后**的低水位(地板在那里,不在启动那一刻)。

## 这条车道上的实测

| 量 | 值 |
|---|---|
| 每 rank 权重 | 占 121.69 GiB 节点预算中的约 98 GiB |
| `MemAvailable` 启动 → 一次长请求之后 | 3.50 → **2.35 GiB** |
| prefill(packed Engram,零 cached token) | **966–1021 tok/s**(2.5 万与 10 万 token 提示) |
| decode,单流 | **35.9–37.9 tok/s** |
| needle,精确匹配 | **128K PASS**(97.9 s) |
| KV 池 | 600K 下 214 万 token(≈ 窗口的 3.6×) |

有一条**顺序效应**值得记下:在 Engram 表打包到节点本地 NVMe **之前**,这条车道上一个
**32K** 的 needle 探针**直接失败**;打包之后 **128K** 通过。在两节点车道上,
Engram 行存储不是"性能锦上添花" —— 对我们而言它是"长上下文不可用"与"长上下文可用"的分界。

## 本地扩展门(给同样用自编译内核跑量化包的人)

如果你自己构建厂商扩展(我们构建 cooperative MoE 内核,是因为发布产物没有公开),那么**厂商自己的门**
才是你该跑的东西,而且要**每节点都跑**:

* 脚本化集成门必须报 `54` 项检查、`status: pass`,**并且每节点退出码为 0** —— 一台通过不代表另一台通过;
* 链式 pin 必须**一次性全部更新**(二进制 pin、适配器自己内嵌的 `SHA256`、以及 profile 生成器校验的适配器哈希);
* 本地重编的 `.so` **不应该**期待与发布 pin 哈希相同 —— 厂商自己就是这么说的,而我们用同一份源码编了三次
  得到三个不同哈希。**授权替换的是门,不是哈希。**

## 本文不主张什么

* 不主张四节点的表格有错 —— 不同车道、不同基座包。
* 不主张 `MAX_NUM_BATCHED_TOKENS` 是普适旋钮 —— 这只是某一个车队上的一次测量。
* 不主张池子地板可迁移:我们 600K 的池子约为窗口的 3.6×,而主 README 那句
  *"KV 池每多 0.5 GiB 就吃掉约 1 GiB 的 head prefill 余量"* 在这里**完全照旧成立**。
