# 2026-09-14 —— 重启可存活的 KV 前缀层、KV 池定容,以及两条没能复现的跨仓结论

三件事,全部在同一个四节点 TP=4 环网、同一权重、同一服务构建上实测:

1. **落在节点本地 NVMe 上的、重启可存活的前缀缓存。** 分层本身 2026-09-13 就在用了;
   仍然坏的是它的索引活在引擎内存里 —— **每次重启都把盘上那些 KV 变成孤儿**,而这套配置
   重启很频繁。本文给出修法、它的价值,以及写错时会**静默产出错误答案**的三个陷阱。
2. **给 KV 池定容**(`--kv-cache-memory-bytes`),让容量不再是抽奖:同样的 flag、同样的空闲
   内存,今天各次起服观测到**六个不同**的池读数。定容后只有一个值,而且比未定容读数的均值
   **大 23 %**。
3. **一次跨仓移植验证。** 另一份公开的两节点配方(同样 GB10 硬件、不同模型)宣称两个
   便宜的收益。两条都在交替 A/B 下测了,**本机都没复现**;仍然写出来,因为现在知道了
   每条结论成立的条件,也因为这套测法本身可以复用。

本报告的规矩与前一份相同:**只在数字可重复时才声称它。** 没能复现的,就标为没能复现。

---

## 一、问题:NVMe 层的索引随进程一起死

分层本身要感谢 **yunwei37/dgx-spark-4-ring-no-switch**(MIT):一份单文件、树外的 vLLM
连接器(`dsv41_kv_nvme.py`),把可缓存的 KV group 落到每节点的 NVMe 槽文件,再按块哈希取回。
接入只需三个命令行产物、无需改动 vLLM 源码,所以我们采用了它。

接入当天的实测:一条 **92,429 token** 的提示(冷)耗时 **59.87 s**;**完全相同**的提示再发
**0.65 s**,追加一句再发 **0.66 s** —— 约 **92 倍**。这正是引擎自带的前缀缓存对这款模型
(压缩缓存环)给不出的多轮行为(它的聚合命中计数在动,但 92 K 重发仍要付全量 prefill)。

缺口在于:块表(哈希 → 槽位)**在进程内**。引擎一重启 —— 在这里每次改配置都会重启 ——
NVMe 文件里仍有数 GB 有效 KV,却没人能寻址。

## 二、修法:一个会给自己索引做快照的树外 cache policy

vLLM 支持从树外挂接 offloading manager 的淘汰策略(`cache_policy` +
`cache_policy_module_path`,按类名解析)。修法就是一个策略子类 + 一个 spec 子类,和分层模块
并列挂载、在连接器配置里按名引用 —— **不动 vLLM 源码**:

```jsonc
"kv_connector_extra_config": {
  "spec_name": "PersistentNVMeOffloadingSpec",       // 我们的子类
  "spec_module_path": "kv_persist_policy",           // 本仓 tools/
  "cache_policy": "PersistentLRUCachePolicy",        // 我们的子类
  "cache_policy_module_path": "kv_persist_policy",
  "nvme_dir": "/kv-offload", "nvme_bytes": 68719476736, "offload_prompt_only": false
}
```
```bash
-e KV_TIER_STATE_PATH=/kv-offload/kv-index.json   # 索引落盘位置
-e KV_TIER_TAG=r0                                 # 按 rank 分命名空间
-e KV_TIER_FINGERPRINT=<checkpoint-and-config-id>  # 任何变更即失效
```

发布文件:[`tools/kv_persist_policy.py`](../tools/kv_persist_policy.py)(MIT,约 180 行)。

**三个陷阱(我们都踩过):**

1. **不要走基类的 `get_manager()`。** 基类构造 manager 时读的是**另一个**配置键
   (`eviction_policy`),而且**根本不传 `cache_policy_module_path`**。于是
   `super().get_manager()` 拿到的是内置 LRU 策略,而快照线程照样在跑,并每 20 秒记一条
   `index snapshot failed ('LRUCachePolicy' object has no attribute '_dirty')`。
   子类必须自己构造 manager。
2. **要恢复的不只是哈希表,还有分配器状态。** 只有 键→槽位 是不够的:manager 的空闲链表与
   已分配计数也必须一起回来,否则活块会被再次分配出去,某个请求会**读到别的请求的 KV
   (静默错答案,没有任何报错)**。发布文件里恢复了 `_free_list`、
   `_num_allocated_blocks`、`_num_evictable_cache_blocks`。
3. **只对"写入已完成"的块做快照**,并给索引加**指纹**(权重、布局、槽位几何、KV dtype、tag)。
   写了一半的槽位永远不该可寻址;在另一份权重下写出的 KV 页永远不该被复用。恢复路径上任何
   异常都必须退化成冷缓存,而不是让引擎起不来。

## 三、它的价值(实测)

| 场景 | 之前 | 之后 |
|---|---|---|
| 92,429-token 提示,**引擎重启后第一个请求** | 58 s(全量 prefill) | **0.86 s** |
| 同进程内重发同一提示 | 0.65 s | 0.65 s |
| 公网路径上 20,202-token 提示,重启后第一次调用 | 13.6 s | **2.42 s** |
| 启动日志 | — | `restored 183974 cached blocks from /kv-offload/kv-index.json` |

索引在有流量时每 20 秒写一次:第一个窗口后 **2.0 MB**;跑了一天基准、缓存 191,962 块后
**16.5 MB**。它的上界是分层的槽位数、不是请求数 —— 淘汰策略仍是同一槽位规模上的 LRU,
槽位满了就淘汰,索引随之收缩。

定容 + 持久化档的闸门结果与上一份报告一致(乱码 30/30、拒绝行为符合配置、质量 29/30)。

## 四、KV 池定容:先量,再钉

未定容、`--gpu-memory-utilization 0.83` 保持不变时,今天各次起服引擎报出的池:
**1,460,513 / 1,638,036 / 2,202,903 / 2,537,044 / 2,609,348** tokens。自称决定池子大小的
那个旋钮并不是全部 —— 引擎自己的启动行说明了原因:

```
Free memory on device (105.9/121.69 GiB) on startup. Desired GPU memory utilization is (0.83, 101.0 GiB).
Actual usage is 91.5 GiB … Available KV cache memory: 8.85 GiB
```

统一内存下驱动需要的是**空闲**页而非可回收页,所以权重与 graph 捕获之后剩下多少会随宿主状态
浮动 —— 池子跟着浮动。

`--kv-cache-memory-bytes` 把抽奖变成定值。**定容的做法是:从一次未定容的起服里读
`Available KV cache memory`,然后钉在它略下方。**

| | 未定容 | 钉在 8.5 GiB(9,126,805,504 B) |
|---|---|---|
| KV 池 | 1.46 M – 2.61 M tokens(每次起服不同) | **2,706,122 tokens,每次都一样** |
| 服务端日志 | 打印 `Available KV cache memory` | 不再打印(钉住即定池) |
| 单流解码 · 代码题 | 58.9 / 62.7 tok/s | 63.0 / 60.3 tok/s |
| c6 聚合 | 132.8 / 144.5 tok/s | 168.4 / 168.9 tok/s |
| 冷 prefill ~8 K 首块延迟 | 10.1 / 10.7 s | 10.1 / 10.0 s |

早先这个 flag **在三个取值上都起不来** —— 失败原因是设得高于真实预算,不是 flag 本身。
统一内存上的 over-commit 需要断电重启,所以定容之前先量。

## 五、起服卫生:池子抽奖的另一半

如果说定容是在**引擎侧**消掉波动,那么一道内存门就是在**引擎之前**消掉它。抄自同一份两节点
配方(它的 `wait_mem` + 页缓存驱逐):

```bash
# 旧容器清掉之后、起服之前:
#   等每个节点 MemAvailable >= 100 GiB,然后驱逐页缓存
sync; echo 3 > /proc/sys/vm/drop_caches     # 需 root;无 root 可用:
#   find <权重目录> -name '*.safetensors' -exec dd if={} iflag=nocache count=0 \;
```

实测:容器死后节点报 **106–110 GiB** 可用,驱逐后 **108–111 GiB**,随后起服立刻过门。
它之所以重要,理由就是第四节的引擎那一行:容器被杀后统一内存要数十秒才回来,往那个窗口里
起服,就是一次幻影 OOM 或一个偏小的池子。

## 六、跨仓移植验证:两条结论,都没复现

来源:**bilikaz/qwen38-flash-next-cluster-recipe**(两个 GB10 节点、TP=2、另一种模型、
上游 vLLM 0.29 + 六个补丁)。其中两条宿主级结论便宜可测,我们用交替 A/B 测了。

### 6.1 `vm.compaction_proactiveness=0` —— 宣称:紧配档 ~10 %

它的机制描述很具体、因此可证伪:后台压实在迁移页,而 Spark 上 GPU 内存**就是**这些页,
于是它看到**每 ~37 秒一次 4–5 秒停顿**。测法:连续四个 1,500-token 解码(约 66 秒,跨两个
周期),记录每块到达间隔。

| `compaction_proactiveness` | 间隔中位 | p99 | 最大 | >0.5 s | tok/s |
|---|---|---|---|---|---|
| 20(默认) | 64 ms | 75 ms | **149 ms** | **0** | 89.0 / 90.6 / 90.9 / 92.5 |
| 0 | 64 ms | 114 ms | 708 ms | 1 | 91.6 / 91.7 / 92.3 / 81.5 |

**本机没有可消除的停顿。** 条件差异在它自己的文档里就能看出来:它跑在空闲约 1 GB 的状态,
而这套部署常年留 3–6 GB,所以引擎里那个"压实者"不是它那台机器上的角色。该设置保留了
(零成本、已持久化到 `/etc/sysctl.d/`、一条命令可回滚),但**本机没有可测量的收益**,
我们不把它算作收益。

### 6.2 绑到快核(`--cpuset-cpus`)—— 宣称:每档并发 +2–3 %

拓扑那条完全对得上:0–4 与 10–14 跑 2808 MHz,5–9 与 15–19 跑 3900 MHz,所以
`--cpuset-cpus=5-9,15-19` 是对的集合。交替 A/B、三对、容器原地更新:

| | 单流(定长计数任务) | c6 聚合 |
|---|---|---|
| 未绑核 | 84.6 tok/s | 166.9 tok/s |
| 绑 5–9,15–19 | 91.3 tok/s | 162.5 tok/s |

两个方向都在动,**区间重叠**(单流 79.1–92.0 对 76.2–92.1)。启动即绑核的档位也出现同样
的散布(单流 60.6/68.5、c6 151.7/156.5)。**在这套部署 ±10 % 的跑间噪声下,±2–3 % 的结论
无法判定**,我们不以收益发布它。参数已经接好(容器 flag 可参数化、可关闭),以便将来在
**启动时**复测 —— 那才是原结论的测法。

### 6.3 真正移植过来的

* **起服内存门**(第五节),
* **池定容**(第四节),
* 以及一个**验收习惯**:它的查看脚本用 HCA 端口计数器对网络接口的 TCP 字节计数器采样,
  以证明真的走了 RDMA 而不是悄悄退回 TCP。同样的测法在这里发布为
  [`tools/rdma_proof.sh`](../tools/rdma_proof.sh):解码时四个节点的 RoCE 端口各自双向
  **69–78 MB/s**,而管理网 TCP 计数为 **0** —— RDMA 是真的,这项检查现在进了验收流程。

## 七、测量纪律(两个自己踩的坑,值得公开)

1. **±10 % 是本部署的噪声底。** 同配置、同提示、同一天:单流解码重复运行落在 52–68 tok/s;
   代码题与散文题因投机接受率不同可差约 2 倍。任何几个百分点的结论都必须用**交替 A/B**
   (在同一时段内交替两种配置)—— 单次前后对比在这个尺度上毫无意义,这正是 6.1 与 6.2 被
   记为"未判定"而不是"收益"的原因。
2. **数流式块 ≠ 数 token。** 投机解码下服务端**每个 SSE 块会带多个 token**;一个数块的客户端
   把 384 token 的答案数成 95,还给出一个看着挺像的"14.9 tok/s"。请用
   `stream_options: {"include_usage": true}`,拿服务端的 `completion_tokens` 除以解码段墙钟。
   同一类 bug 的另一个变体 —— 把 token 数除以一段**已含 prefill** 的墙钟、然后又除了一次 ——
   在一套实际跑到 165 tok/s 的栈上报出 12 tok/s。
