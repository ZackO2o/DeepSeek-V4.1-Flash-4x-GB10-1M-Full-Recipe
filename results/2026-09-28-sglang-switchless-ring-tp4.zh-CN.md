# 2026-09-28 —— DeepSeek-V4.1-Flash 的无交换机环网 TP4 lane(SGLang),并与上游环网数据同口径对照

同一档机器、**换了一个引擎**上的第二条 lane:SGLang 的 1M TP4 配置跑在
**无交换机 4 节点环网**上(没有 RoCE 交换机,四台 GB10 点对点成环)。
本文发布我们在这条 lane 上的实测、它相对上游项目**用同一套 harness** 发布的环网
数据的对照,以及三个害我们熬了一夜的运维发现。

README 的头条配置是 **vLLM** lane。这是另一条。本文任何数字都不替代 vLLM 数据 ——
两者引擎不同,更要紧的是**测量 harness 不同**,因此二者彼此不可直接比(见 §5)。

## 一、这条 lane

| | |
|---|---|
| 模型 | `deepseek-ai/DeepSeek-V4.1-Flash`(官方 FP8 权重,未改动) |
| 硬件 | 4 × GB10 / SM 12.1,每台 128 GB 统一内存 |
| 网络 | **无交换机环网**,200 GbE CX7,MTU 9000,每条链路一个 /30 |
| 引擎 | SGLang TP4,社区 `canary-roce` 配置 + `sparkring` 无交换机 NCCL 覆盖层(NCCL 2.30.7) |
| 上下文 | `1,048,576` |
| KV 池 | 定容 `8,000,000`;实际**分配到 3,253,248 token**(见 §4) |
| 并发请求数 | `16` |
| 分块 prefill | `4096` |
| 投机解码 | DSpark `k=5` |
| 显存分数 | 静态 `0.80`(头部 `+0.80`) |
| 内核 / 驱动 | 四台均为 `6.17.0-1029` / `6.17.0-1031-nvidia`,驱动 `580.173.02` |

环网专属、容易漏掉的前提:RoCE all-reduce 路径必须**关掉**
(`SGLANG_ROCE_ALLREDUCE=0`,因为环网靠打过补丁的 NCCL 覆盖层承载集合通信);
覆盖层目录必须是**扁平的**且库内含环网标记串;共享存储权重加载应当关闭
(`NFS_SHARE=0`)并改用节点本地副本 —— 一台边读权重边跑集合通信的环网节点,是在和
自己的通信抢带宽。

## 二、解码实测(与上游环网笔记同一套 harness)

方法:上游项目自己的 `benchmarks/decode_window.py`,**未做任何修改**,打向集群的
网关端点;greedy、关闭思考、每轮开始前服务空闲(`running=0 waiting=0`)。
聚合列 = 墙钟 `completion_tokens / 耗时`,取自**服务端** usage 块;
单流列 = harness 自带的按字符缩放的窗口估计值(口径警告见 §5)。

| 并发 | 聚合 tok/s | 单流中位窗口 tok/s | TTFT | 成功 |
|---|---:|---:|---:|---:|
| 1 | **104.10** | 101.02 | 0.301 s | 1/1 |
| 2 | **147.56** | 70.68 | 0.409 s | 2/2 |
| 4 | **190.00** | 48.60 | 0.455 s | 4/4 |
| 8 | **245.98** | 33.80 | 0.518 s | 8/8 |

在 §4 那次 KV 池调整**之前**同样跑过一遍,聚合读数为
`105.1 / 139.19 / 201.70 / 252.40`(C1/C2/C4/C8)—— 也就是说这套扫描在两个方向上
都可复现到几个百分点,而池子改动**没有**移动解码速度(它是容量,不是速度)。

## 三、与上游环网数据对照(同 harness)

上游项目发布了自己的无交换机环网扫描,用的是同一套 harness(`decode_window.py`),
在另一个四节点环上测得:

| 并发 | 我们(聚合) | 上游环网(聚合) | 差值 |
|---|---:|---:|---:|
| 1 | **104.10** | 74.03 | **+41 %** |
| 2 | **147.56** | 111.48 | +32 % |
| 4 | **190.00** | 160.05 | +19 % |
| 8 | **245.98** | 224.84 | +9 % |

**保持相同**的部分:同一族 checkpoint、同一套 harness、同一指标定义、同一客户端
路径(HTTP 流式经网关)、同一代 kernel/驱动。

**未保持相同**的部分 —— 这也是为什么它是一次对照,而不是"架构更优"的结论:

1. **检出版本不同。** 上游环网扫描测于较早的 SGLang 树(`chunk prefill 1024`、
   `max_running_requests 8`)。我们跑的是当前 `canary-roce` 配置(`chunk prefill
   4096`、chunked indexer、prefill sequence parallel、L2 prefetch、autotune-keep、
   `max_running_requests 16`)。TTFT 那一档的差距主要来自这里。
2. **时钟策略不同。** 他们的节点被 `nvidia-smi -lgc 0,2200` 限住,实测
   **2177–2190 MHz**;我们是 `-lgc 2400,2400`,实测 **2392–2398 MHz**(+9.5 %)。
   他们自己的文档也写明,该上限在**带宽受限**的 step 上只值约 −0.7…−1.5 % ——
   所以时钟能解释 C1 差距中的一小部分,不是全部。
3. **机器不同。** 他们的数字测于"Carlos 的环";我们测于我们自己的环。线材、温度、
   个体差异都没有控制,也无法从结果里剥离。
4. **TTFT 是最弱的一列。** 他们的 TTFT 来自**旧版按字符缩放的估计器**(他们自己
   有注明);而当前 harness 是在首个非空正文事件处计时,我们的列就是这个定义。
   所以 TTFT 对照只能当参考,不能当"快 1.8 倍"的主张。**严格可比的只有聚合列**,
   因为两侧都取自服务端的最终 token usage。

## 3b. 冷 prefill

方法:每个尺寸一次请求、每个请求唯一 nonce(无任何可缓存前缀)、流式、`max_tokens=1`(墙钟即 prefill
加一步解码);tok/s = **服务端上报的** `prompt_tokens` / TTFT。filler 用**高熵随机词** —— 每个 token
命中不同的 Engram 行 —— 刻意**不用**某些 prefill 表所用的单 token 合成 filler:在
`DSV41_CACHE_GIB=0` 的机器上,那种 filler 主要量的是行存储而不是 prefill(见 §4)。

| prompt tokens | TTFT | prefill tok/s |
|---:|---:|---:|
| 4,159 | 1.11 s | 3,732 |
| 16,327 | 3.53 s | 4,629 |
| 32,709 | 7.03 s | 4,656 |
| 65,176 | 13.91 s | 4,685 |
| 130,913 | 29.74 s | 4,402 |
| 261,416 | 64.11 s | 4,077 |

峰值 **~4,700 tok/s**(16k–64k 段),而且到关键区间仍未塌:同一配置更长的一轮实测 408,462 token 用
109.1 s(**3,744 tok/s**)、**818,377 token 用 254.0 s(3,222 tok/s)** —— 到 80 万 token 都没有断崖。

**重复 filler 对照组**在同一配置上,25,250 与 100,868 token 分别读 **5,041 / 5,054 tok/s** ——
单 token filler 在这里比高熵 filler **快约 7%**。这与促使我们采用此方法的那个上游结论是**另一根轴**
(他们比的是 filler 上的 *cache 设置*,只有关缓存时 filler 才慢),所以我们把它记为观察而非矛盾——
重复 token 本身也会让注意力路径退化。

**这条 lane 在 prefill 上的位置。** 上游项目为其*环网*档发布的是 **16k–128k 为 5,393–5,567 tok/s、
262k 为 4,971**,用他们自己的加载器与单 token filler 测得。我们比这低约 **15%**(若用我们的重复
filler 对照读,则低约 7–9%)—— 这与 decode 的方向**正好相反**:同一项目中,我们在 decode 上是领先的。
我们的数是本地 API 客户端的 TTFT 口径、不是他们的加载器,所以请把它当成**线索而非定论**:
prefill 是这条 lane 上第一个值得调的东西,而上游项目也指出环网的成本正落在大 prefill 集合通信上。

**前缀缓存,同一 lane:** 重复同一个 130,831 token 的请求只用 **0.51 s 而不是 28.8 s** ——
前缀全命中时 TTFT 降 56 倍。

## 四、KV 池:定容值不等于实配值

`MAX_TOTAL_TOKENS` 定容在 `8,000,000`,但引擎在 CUDA graph 捕获、视觉/工具路径
之后真正分配的远小于它。两行数据值得记:

| `DSV41_CACHE_GIB` | 实际分配 KV 池 | 起服后 host MemAvailable |
|---|---:|---:|
| `4`(我们模板里的默认值) | 2,977,536 token | 13.67 GiB |
| **`0`** | **3,253,248 token** | **15.22 GiB** |

即同样配置下 **池子 +9 %**、余量多约 1.5 GiB,改动只是把这个值从 `4` 改成 `0` ——
上游项目当前参数表里本来就写的 `0`,理由一致:在 GB10 上
**host 内存就是显存**,把几 GiB 花在行缓存上,不如留作起服/推理余量,
比那点命中率值钱。我们当初是从旧模板继承来的 `4`。

实用规则:量**实际拿到的池子**(服务端启动日志里的 `max_total_num_tokens`),
而不是你请求的那个数 —— "昨天能起、今天起不来"就活在两者之差里。

## 五、运维环网的三条发现

### 5.1 采样网卡 **carrier**,不要只看 IB 端口状态

环网有一条链路在间歇性掉线。那个设备上的 IB 端口状态多数时间读数是 `4 (ACTIVE)`
—— 也就是大家都会看的那一项 —— 而同一物理口的**网卡 carrier** 正以 4 秒的采样
间隔反复 `1 → 0 → 0 → 1 → 0`。它在上游造成的症状明确且昂贵:RoCE 异步线程打出
约 1300 条 `Got non-fatal async event` 告警、起服时 `ibv_modify_qp` 超时、
以及在集合通信建立阶段就死掉的多次启动。

物理重新插拔该线之后:连续多次采样 carrier 稳定、端口速率回到 200 Gb/s、
异步告警 **1300 → 0**、起服干净。

**价值要说实话:** 解码吞吐并没有变(我们自己的快速 harness 上是 58.9 → 58.6)。
收益是**拆掉了一颗地雷**,不是多出来的 tok/s。如果环网起服不稳,先逐口、**反复**
采样 carrier 再怀疑 NCCL —— 单次读数没有任何意义。

### 5.2 写死的 RoCE GID 下标,一碰硬件就过期

我们的 NCCL 覆盖层配置了 `NCCL_IB_GID_INDEX=3`,而且连续数周都是对的。
在上面那次重新插拔之后,**RoCEv2 的 IPv4 GID 在四台机器上都挪到了下标 4**,
起服门直接失败:*"no common IPv4 RoCE v2 GID"*。配置一个字没改,硬件状态变了。

规则:任何线缆、端口、上断电事件之后,重新探测每台机器上**哪个 GID 下标**
真正承载环网 IPv4 地址,再更新环境变量后起服。不要把它当常量 ——
它是当前设备状态的属性。

### 5.3 软挂载会把健康检查骗过去

两个环网节点报告权重挂载存在,而对它 `ls` 会永久阻塞 —— 这是共享存储消失后
残留的软挂载条目。`mountpoint` 判定会说"已挂载";随后起服就报
*"weights missing/incomplete"*。此类挂载上的探针必须套 `timeout`,而健康判据必须是
**产物形状**而不是挂载形状:去数 checkpoint 分片(这个 checkpoint 是 48 片),
而不是问某个路径是不是挂载点。

## 六、两个负结果

1. **一份第三方"仅环网"的 NCCL 构建没有迁移过来。** 另一个 4 × GB10 项目提供了
   针对环网优化的 NCCL 构建;在我们的栈上,用它起服会失败并报
   `NCCL error: invalid usage`。一次单变量试验 —— **只换库、环境一字不改** ——
   就能复现该失败,说明成因是那份构建自身的前置假设,而不是同一次试验里捆进来的
   那些调参项。那个项目文档里配有一个绑核 shim;我们没有编它,也**没有**单独隔离
   那些额外的 NCCL 参数(buffer size、channel 数、tuner 阈值、protocol mask),
   所以它们在此处是**未经测试**,而不是"已知有问题"。那份工作的功劳照旧归属原作者
   —— 它只是不能直接落进这条 lane。
2. **"用满四个 HCA 设备"的前提是我们并不运行的那种网络。** 每节点暴露四个 RoCE
   设备(而非两个)的建议会在我们的起服门处失败:它要求四个设备上存在共同的
   IPv4 RoCEv2 GID,而单平面环网里第二个平面的设备根本没有环网地址。把环网拆到两个
   平面上(并给两个平面都配上地址)是一次网络重配,不是一个开关;我们保持两个设备,
   并把这个建议记为"不适用",而不是"错误"。

## 七、复现

基准脚本是上游项目的,原样使用;请直接指向它们,而不要自己重写:

```bash
# 集群空闲;关闭思考;greedy
BASE_URL=http://127.0.0.1:8888 python3 benchmarks/decode_window.py
```

我们贡献的是两个探针,刻意写得笨一点:

- `tools/ring_link_health.sh` —— 逐口采样 `carrier` / IB 状态 / 速率
  (重复 N 次;一次读数什么都证明不了)。
- `tools/post_reseat_recover.sh` —— 线缆或断电事件之后:按分片数修复权重挂载、
  探测当前 RoCEv2 IPv4 GID 下标,然后重启并过闸。
